Identity & platform architecture

One identity layer, eighteen applications

~30% faster project onboarding

Problem

A national grocery retailer had grown a set of internal applications — warehouse, store operations, HR, contracts, BI, communications — each with its own login and its own idea of who a user was. Every new application meant re-implementing authentication, and permissions drifted apart between them. Onboarding a new system meant onboarding its users all over again.

Approach

  • A central authentication and authorisation service as the single source of identity.
  • Office staff recognised through Active Directory integration — no password prompt at all.
  • A separate badge-and-password path for shop-floor terminals outside the domain.
  • Short-lived tokens for application-to-application handoff, so a user never re-authenticates when moving between systems.
  • Permission trees defined per service from a template, rather than hard-coded per application.
  • Roles derived from the org chart itself: if the directory says people report to you, the system treats you as their approver — no parallel permission bureaucracy to maintain.

Outcome

Eighteen applications behind one identity and one permission model, served under a single domain with path-based routing. Adding an application became a matter of registering a service and declaring its permission tree — no new authentication code, and no new place for permissions to go stale. Redundant auth systems were retired.

Where the 30% comes from Every new application used to ship its own login screen, its own user table and its own permission logic, then wait on IT to populate it — roughly a third of the setup work before anyone could log in. That work is now zero. The saving is the removal of a fixed step, not developers going faster.

Architecture — metadata over code

A configurator that removed the release cycle

~10× faster module delivery

Problem

Every new ERP module — and every customer-specific variation of an existing one — meant a code change, a build, a regression pass and a deployment window. The bottleneck was not the difficulty of the modules. It was that trivial differences between deployments all had to travel through the same release pipeline.

Approach

  • Moved the definition of screens, fields, validation and behaviour out of compiled code and into SQL metadata that the platform reads at runtime.
  • A configurator engine interprets that metadata, so a new module is authored as data rather than built as an assembly — no recompilation.
  • The same principle reused for the reporting engine: an administrator turns a reviewed SQL query into a report with filters, tables and charts, without a developer in the loop.
  • Guardrails kept the flexibility from becoming chaos — metadata is versioned and reviewed, and the engine refuses configurations it cannot serve safely.

Outcome

New module creation and feature delivery accelerated by roughly a factor of ten across retail operations. The architectural bet — data over code for anything that varies per customer — is the same one underneath my own commercial ERP product, where it removes the need for a code branch per client.

Where the 10× comes from Not developers typing faster. A module used to need a code change, a build, a regression pass and a slot in a deployment window — days of calendar time, most of it waiting. Authored as metadata, the same module is live the same day. What was removed is the release cycle; the design work is unchanged.

Point of sale & regulatory compliance

A till that satisfies a national tax authority

200+ businesses · −35% merchant cost

Problem

Point-of-sale software has to register every sale with the state in a form that can later be audited. Certification is not a feature — an uncertified till cannot legally take money. At the same time a shop cannot stop selling because a network link dropped, and a receipt that was taken offline still has to be provably accounted for.

Approach

  • Fiscal registration designed into the transaction path, not bolted on as a nightly batch.
  • A local offline queue keeps the till trading when the fiscal service is unreachable, then reconciles on reconnect — the same offline-first pattern I had built earlier for field-sales agents.
  • Reconciliation between each till's local database and the central ERP, with differences surfaced and correctable rather than silently absorbed.
  • A second-generation build targeting Android kiosk hardware alongside Windows, sharing the transaction core.
  • One integration surface for the whole payment landscape — national e-invoicing, certified fiscal devices, four bank terminal networks, a cashless wallet and a loyalty scheme — so a merchant does not buy and wire five separate boxes.

Outcome

State-approved online cash register operator status, deployed at 200+ businesses and reducing merchant hardware and integration cost by around 35% — because the integrations that used to be bought separately came with the product. This is my own product, not employer work, so the architecture, licensing, installer, printing service and the certification itself are all mine.

Where the 35% comes from Arithmetic rather than estimate. A merchant opening a till used to buy and integrate five things separately — the fiscal device, the e-invoicing connection, the bank terminal link, the cashless wallet and the loyalty scheme — each with its own vendor, hardware and integration fee. They now arrive with the product. The saving is the four purchases that no longer happen.

Why this is relevant in Germany. This is structurally the same problem as TSE / KassenSichV: a certified security element in the receipt path, an offline mode that cannot lose transactions, and an audit trail that must hold up years later. The regulation differs; the engineering does not.

Systems integration

Making systems talk that were never meant to meet

3 production services, one template

Problem

A quick-service restaurant operator ran point of sale on one vendor's Oracle stack, finance and inventory on a second vendor's PostgreSQL ERP, and procurement in SAP. Sales, goods receipts and stock movements had to cross all three — and were crossing them by hand.

Approach

  • Small, single-purpose services rather than one integration monolith: a POS-to-ERP sales sync running as a Windows service; a REST gateway accepting goods-receipt pushes from SAP and writing ERP delivery notes; a receipt sync module.
  • All three on one shared Clean Architecture template, so the fourth flow is a module rather than a new system.
  • Compiled with Native AOT — instant start, no runtime installed on the host, smaller attack surface, and a binary that does not casually decompile.
  • Production databases treated as read-only until a write path has been explicitly reviewed and approved. Where a record already existed correctly, the integration annotates its source instead of rewriting it.

Outcome

Three production integration services on a common template. Manual re-keying between the three systems removed for the flows that were migrated, and each new document type became a bounded, testable addition rather than a negotiation.

Real-time monitoring

Seeing a till fail before the queue does

~800 terminals · near-zero downtime

Problem

Across 150+ stores and roughly 800 POS terminals, the first signal that a till had failed was usually a phone call from a store manager with a queue forming behind them. By then the fault was already costing sales, and nobody centrally knew how often it happened or where.

Approach

  • Live telemetry streamed from every terminal to a central service and pushed to the browser over Server-Sent Events, so a dashboard can sit on a command-centre video wall all day without being refreshed.
  • Detection of sales that exist on a till but never reached the central ERP, with one-click and bulk re-synchronisation instead of a manual investigation.
  • VAT-rate mismatches between store and central master data surfaced as a list to be corrected, not as a report nobody reads.
  • Reviewed SQL execution across many stores at once for diagnosis, with read and write separated by permission and every execution written to an audit log. Connection strings never leave the server.

Outcome

Hardware faults now announce themselves on the wall in the command centre rather than over the phone, and terminal downtime dropped to near zero. The same service became the place where store-versus-centre data disagreements get reconciled.

What "near zero" actually means Repair time did not change — detection time did. A fault used to be discovered by a customer standing in a queue and reported by phone; it now appears on the wall within seconds of the terminal going quiet. The downtime that disappeared is the interval between failing and anyone knowing.

Legacy migration

Retiring a spreadsheet that had become infrastructure

Millions of records · zero downtime

Problem

Two migrations, one lesson. Millions of legacy enterprise records had to move onto a new database and microservice landscape without the business pausing. Separately, in-store product placement across 150+ stores — which brand sits on which stand, under which contract, physically checked each month — ran on spreadsheets, scripts and shared drive folders. Both were load-bearing. Neither could simply be switched off.

Approach

  • Phased cutover rather than a big-bang weekend: old and new paths run together, traffic moves in slices, and every slice is reversible until it has proven itself.
  • Data integrity verified continuously during the move, not signed off once at the end.
  • For the placement system, the store floor plan became the interface: placements as pins, moved by dragging, with zoom and pan.
  • The monthly physical check became a guided flow with photo evidence and an approval step, so a completed check is a record rather than a claim.
  • Automatic alerts for incomplete placements and contracts approaching expiry — the two failure modes the spreadsheet could not see.

Outcome

Millions of records migrated with full integrity and no business disruption, and the placement process moved onto a system with enforced rules and an audit trail while field teams kept working. The migration risk — not the feature list — was the hard part, and it is the part I would want to be asked about.

Why "zero downtime" is a method, not luck There was never a cutover window, because there was never a moment when only one path existed. Old and new ran together, traffic moved in slices, and every slice stayed reversible until its data had been verified against the source. A slice that misbehaved was rolled back without the business noticing.

Applied AI

AI as a working part of the product

MCP servers in team use

Problem

Three different questions. An ERP holds everything a business knows, but an AI assistant cannot reach any of it. Developers using AI tools produce code fast and inconsistently, drifting away from the architecture the platform depends on. And a bakery distribution business decides every morning how many loaves each van carries to each customer — too few loses a sale, too many is waste by evening.

Approach

  • MCP servers exposing ERP operations to AI agents, so an assistant can query and act on real business data instead of guessing.
  • The same servers carry the guardrails: code, UI and queries generated in Claude, Cursor or Gemini conform to company architecture standards and security rules automatically, rather than being corrected in review.
  • A daily order-planning engine recommending an exact quantity per rep, customer, product and date — and writing a one-sentence explanation in the operator's own language, so the number can be argued with rather than obeyed.
  • A newsvendor model over the demand distribution, with ABC customer profiling, product shelf life and damped feedback calibration against what actually sold.
  • One rule deliberately asymmetric and enforced in code: never recommend below what already sold, and actively reduce returns. A symmetric "don't change much" rule would have been easier and wrong.

Outcome

A forecasting service in production with a covering unit-test suite, an ERP an AI agent can operate, and MCP servers deployed across software teams. I use AI-assisted development daily — as the reviewer of its output, not a passenger.

06 — Quality & delivery

How the work is kept honest

Testing

Unit and integration tests with xUnit and NUnit, kept fast enough to run on every change — the forecasting engine's suite runs in well under a second, which is the only reason it actually gets run. For business rules that must never bend, the test is written against the rule, not the implementation.

Safety at the boundary

Production databases are read-only until a write path is explicitly reviewed. File uploads are validated by real content type rather than filename. Uniqueness that matters is enforced by a database constraint, not by application logic that a race condition can slip past. Credentials never reach the browser.

Documentation

Every significant system here has a written architecture and an operator guide — the desk-booking project runs to eleven documents, the accounting module to nine. If a system cannot be explained to the person who has to run it at seven in the morning, it is not finished.

On my own product that meant architecture, licensing, installer, printing service, typeface and the fiscal certification. I am comfortable being the person responsible when something is unclear, and I would rather ask a blunt question early than deliver a confident guess.

I started on the customer's side

Three years rolling out ERP at customer sites — requirements, configuration, training — before I designed any of it. It is why I write for the person at the till and the warehouse worker with a handheld, not for the architecture diagram.

I migrate carefully

Most of my work replaced something already running a business. The interesting engineering is rarely the new feature — it is keeping the old path alive until the new one has earned the traffic, and being able to reverse a slice that misbehaves.

I say what I don't know

My depth is .NET, SQL Server, integration and ERP domain. I have not run large-scale cloud infrastructure in production and I will not claim it. What I do have is a long record of learning a system well enough to be trusted with it — and I am currently closing that gap deliberately rather than pretending it is not there.
